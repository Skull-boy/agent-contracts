# Threat Model: Scyvera Distribution, Conformance & Registry Integrity (T11 – T14)

This document extends the runtime threat model ([`threat-model-enforcer.md`](threat-model-enforcer.md)) and the lifecycle threat model ([`threat-model-lifecycle.md`](threat-model-lifecycle.md)) with threats introduced when Scyvera is **distributed as installable artifacts** (skills, plugins, wheels, registries, evals). Formalized alongside RFC 0003.

Each threat below is scoped to the **distribution layer**: the moment the contract, the schema, the enforcer package, or a conformance result leaves the trusted repository boundary and travels through stores, registries, package managers, or agent harnesses.

---

## Summary of Threats & Mitigations

| Threat ID | Threat Name | Layer | Mitigation Mechanism | Status |
|---|---|---|---|---|
| **T11** | Dependency Confusion in Gateway / Optional Adapters | Packaging / Install Chain | Optional extras kept dependency-light; pinned version floors; SBOM + signed release attestation | Planned (RFC 0003, Phase 1) |
| **T12** | Contract Substitution via Prompt Injection | Agent Runtime / File System | Re-seal ritual: any contract *re-generation* must pass through approved authoring flow, be re-validated, re-registered, and re-attested; enforcer detects unregistered contract identity at gate time | Planned (RFC 0003, Phase 1 / Phase 3) |
| **T13** | Registry History Rewrite without Deletion | Contract Registry | Hash-chained `registry.jsonl` (`prev_hash` per entry) + `registry.verify_chain()`; chain break fails closed | Planned (RFC 0003, Phase 1) |
| **T14** | Symlink / Path Abuse in Contract Loading | File System / Loader | Canonicalized path resolution at load; contract directory must be the resolved owner of `contract.yaml`; loader refuses files reached through symlinks outside the declared workspace | Planned (RFC 0003, Phase 1) |

## Detailed Threat Analysis

### Threat T11: Dependency Confusion in Gateway / Optional Adapters
- **Description**: A consumer's dependency resolution pulls a malicious or spoofed package impersonating a Scyvera optional adapter (`PyGithub`, `qdrant-client`) or a similarly-named community extension during `pip install "scyvera[all]"`, injecting code at the same trust boundary the gateway is designed to protect.
- **Mitigation & Invariant**:
  - Core package remains dependency-light (declared in `pyproject.toml`: only `PyYAML` and `jsonschema`); optional adapters are never imported in core install paths.
  - Release pipeline (RFC 0003 §C6) publishes a **signed attestation** binding `{wheel hash, schema version, adapter floors}` with every release, plus an SBOM.
  - Consumers can verify an installed distribution with `scyvera self-check` against the attested manifest before trusting the runtime enforcer.

### Threat T12: Contract Substitution via Prompt Injection
- **Description**: An agent under prompt injection is instructed to "update its own contract" — regenerating `contract.yaml` with broadened permissions or removed approval points, then reloading it (a stateful variant of T5 that survives the after-load integrity check by recreating the file instead of mutating it).
- **Mitigation & Invariant**:
  - **Re-seal ritual**: contract regeneration is treated as a *status change event*, not an ordinary file write. A newly generated contract MUST be re-validated, re-linted, registered into the `ContractRegistry` (new version with schema + hash), and recorded as a lifecycle event in the audit log.
  - At gate time, an enforcer created from a file MUST be able to cross-check its `contract_hash` against the registry entry for that `node_id`; a mismatch between the running contract and the latest registered intent is a retriable alert (`ContractRegistry` provides `get_latest(node_id)`).
  - Contracts whose lifecycle declares `initiation: human-only` MUST NOT be regenerated by agent-initiated flows; loaders emit a registry identity warning when a contract appears that was never registered.

### Threat T13: Registry History Rewrite without Deletion
- **Description**: An attacker with write access to `.scyvera/registry.jsonl` cannot easily delete the append-only store (detectable via `size()` / `has_hash()`), but CAN **insert reconstructed entries** or rewrite the file with fabricated-but-plausible history — gaining the same audit deception without any "deletion."
- **Mitigation & Invariant**:
  - Each registry line carries `prev_hash`: the SHA-256 of the preceding entry, chaining the store into a tamper-evident sequence.
  - `ContractRegistry.verify_chain()` recomputes the chain over the file; any swap, splice, or reorder breaks verification and raises `RegistryError` (fail closed), consistent with the registry's existing fail-closed error policy.
  - Chain verification is required before registry queries answer provenance questions ("what governed this node at time X").

### Threat T14: Symlink / Path Abuse in Contract Loading
- **Description**: `contract.yaml` is a symbolic link pointing outside the workspace (or a joined path escapes the declared contract directory), causing the enforcer to seal and enforce a contract the integrator never reviewed.
- **Mitigation & Invariant**:
  - `ContractEnforcer.load()` resolves the canonical absolute path of `contract.yaml` and refuses loading when the resolved path escapes the requesting directory boundary.
  - Integrity verification (`verify_integrity()`, T5) continues to compare against the canonical resolved path, not the linker-visible path, so post-load replacement via symlink redirection is also caught.
  - This closes a known attribute of the current "contract.yml vs contract.yaml" precedent (the 0.2.0 cleanup): naming/path confusion is already treated as a load-time error, and the same policy extends to escape attempts.

## Threat Propagation Map

| New Threat | Interacts With | Why |
|---|---|---|
| T12 | T5 (file replacement), T10 (version confusion) | Both are "the enforced contract is not the contract someone approved" — T12 attacks it through the authoring pipeline rather than the file. |
| T13 | T9 (audit tampering) | Registry lines are the audit analog at the registry layer; the same freeze property (append-only) needs a stronger structural chain than policy. |
| T14 | T7 (injection) | T14 is a path-injection variant; closed pattern matching (T7) covers identity strings, and canonical path resolution covers escaping via the filesystem. |
| T11 | T4 (gate bypass) | A compromised adapter often gets a direct ungated reference to the same SDK clients the gateway isolates — attestation keeps the supply chain inside the trust boundary. |

---

## Scope & Non-Goals

This threat model does **not** claim mitigation of:
- Arbitrary code execution inside the host runtime before Scyvera loads.
- The documented T4-adjacent limitation that an integrator may still call ungated application-layer functions.
- Integrity of contract **content semantics** (T6 remains a peer-review and conformance-check concern, explored in RFC 0003's Tier 1 static checks).

Distribution artifacts (skills, plugins, eval suites) inherit these residual risks and MUST document them in their own manifests.
